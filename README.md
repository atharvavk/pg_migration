# pg_repl — zero-downtime switchover between two Postgres instances

Two Postgres 18 clusters on ports **5432 (db1)** and **5433 (db2)**, connected by
logical replication, with **pgbouncer (port 6432)** as the only database address
the application ever connects to. Traffic is migrated from db1 to db2
(with zero failed transactions) by pausing the proxy, draining in-flight
transactions, catching up replication, and resuming against db2.

```
                     ┌───────────────►  db1  127.0.0.1:5432  (initial primary)
 app ──► pgbouncer ──┤
 6432    (proxy)     └───────────────►  db2  127.0.0.1:5433  (target)
```

Logical replication underneath:

```
 db1 ──pub_names──► sub_names_forward ──► db2    (always on)
 db2 ──pub_names──► sub_names_reverse ──► db1    (armed for post-switch writes)
```

---

## 1. Why this works (the mechanics)

### 1.1 pgbouncer `PAUSE` = drain + buffer, the designed behavior

- `pool_mode = transaction`: a server (postgres) connection is bound to a client
  only while that client has an **open transaction**; on `COMMIT`/`ROLLBACK` it
  is returned to the pool.
- `PAUSE` (issued on the `pgbouncer` admin console) does two things:
  1. stops *granting* server connections to new client requests, and
  2. **waits until every open transaction has finished** and its server
     connection has been closed. It blocks until then — the console command
     simply doesn't return while anything is in flight.
- Clients that connect (or send queries) while the proxy is paused are
  **buffered**: the TCP connection is accepted but nothing is executed yet.
  They are NOT rejected — they just stall, which is why p95 latency measured
  by the fixture spikes during the switch window and then everything proceeds.
- `RESUME` un-pauses. Because the config is `RELOAD`ed *while still paused*,
  buffered (and new) transactions are served from the **new** target.

So the sequence that runs in `switchover.sh` is:

```
PAUSE      ── waits for ~10s-held transactions to drain (blocking)
RELOAD     ── [databases] appdb now points at 5433
RESUME     ── buffered txs replay against 5433
```

Note what `PAUSE` does NOT wait for: idle client connections that aren't inside
a transaction are irrelevant (there are no server connections bound to them).

### 1.2 Logical replication setup

- `wal_level = logical` on **both** instances (both fire publications).
- `pub_names` — a scoped publication: `FOR TABLE public.names`.
- `sub_names_forward` (on db2, to db1, `copy_data=true`) — gets the initial copy,
  then continuous change streaming.
- `sub_names_reverse` (on db1, to db2, `copy_data=false`, `origin='none'`) —
  lets writes made *after* the switchover (on db2) replicate back to db1.
- Both subscriptions use `origin = 'none'`, meaning "only apply changes that
  were made locally on the publisher". This is what makes bidirectional
  replication loop-free: otherwise db1 would re-apply db2's copy of db1's own
  writes back-and-forth, or PK-conflict on `names`.

Each `CREATE SUBSCRIPTION` creates a logical replication slot on the publisher.
The slots are how `switchover.sh` verifies "everything made it across".

### 1.3 The sequence gotcha (this is the one that bites everyone)

Sequences are **not** replicated by logical replication. `names.id` is
`GENERATED BY DEFAULT AS IDENTITY`, so an insert on db1 does
`nextval('names_id_seq')` on db1 only. At switchover, db2's local sequence is
still wherever it was seeded — mid-run, potentially *behind* the replicated
max(id). The first insert on db2 would then try to reuse an id that already
exists on db2 → PK violation → the app crashes seconds after assume-standby.

Fix: during the drain window (once writes have stopped on the old primary so
the value can't move), read `(last_value, is_called)` from the old instance and
`setval` db2's sequence to match. That's step `[3/6]` in `switchover.sh`.

### 1.4 The catch-up verification (what makes the switch actually safe)

Ordering matters: the LSN to wait for must be captured **after** the drain has
fully finished — an in-flight 10s transaction that commits *after* pause has
"completed" would otherwise fall outside the comparison.

`switchover.sh` therefore:
1. waits for `PAUSE` to complete (drain done, writes stopped on old primary),
2. captures `pg_current_wal_lsn()` on the old primary,
3. loops on `pg_wal_lsn_diff(confirmed_flush_lsn, captured_lsn)` for the slot
   used by the direction's subscription on the new target's side, until ≤ 0.

Only then does it `RELOAD`/`RESUME`.

### 1.5 Pool sizing note

5 goroutines/sec × 10s hold each = ~50 concurrent open transactions. In
transaction pool mode each occupies one server connection for its lifetime, so
`default_pool_size = 64` (+ reserve 16) keeps them all parallel. Set
`max_client_conn = 500` so during a pause many clients can buffer at once, and
`query_wait_timeout = 120` so buffered transactions have room to sit (they end
up waiting only ~10s in practice, but leave headroom).

lib/pq is used on purpose: it doesn't cache prepared statements across
transactions, so it is safe under transaction pooling (pgx's default statement
caching is not, unless configured).

## 2. Files

| file | role |
|---|---|
| `bootstrap_clusters.sh` | `initdb`s db1/db2 when missing (fresh clone); never deletes existing data |
| `pgbouncer/pgbouncer.ini.template` | proxy config template; the `appdb = ...` target line is what switchover rewrites |
| `pgbouncer/pgbouncer.ini` + `userlist.txt` | **generated** at setup time from the template (gitignored) |
| `setup_replication.sh` | one-time setup: wal_level, schema, pub/sub, sequence seed. Idempotent. |
| `switchover.sh <5432\|5433>` | the runbook, scripted. Symmetric in both directions. |
| `app/main.go` | load generator (5 goroutines/sec, 10s-held tx, INSERT+UPDATE) |
| `run_test.sh [dur] [switch_at]` | orchestrator: build, start pgbouncer, run load, switch mid-run, assert results |

**Identity model** (no usernames are baked into the repo):
- `PGUSER` env var — the postgres superuser everything runs as; defaults to the
  invoking OS user (`$(whoami)`), which `initdb` also uses as the bootstrap
  superuser. On a fresh clone we can run with `PGUSER=postgres` or whatever
  role matches our setup.
- `pgbadmin` — pgbouncer-internal account (exists only in the generated
  `userlist.txt`) used for the admin console.
- Ports: `PGPORT_A`/`PGPORT_B`/`GBPORT` env overrides (default 5432/5433/6432).

## 3. Running it

Prerequisites on PATH: `initdb`/`pg_ctl`/`psql` (postgres 16+ is fine, tested on
18), `pgbouncer`, and `go` for the load generator.

On a fresh clone, `./setup_replication.sh` is the whole dance: it bootstraps
the two clusters first (via `bootstrap_clusters.sh`, skipping any that exist),
then applies wal_level, schema, publication/two subscriptions, and the
sequence seed.

```bash
./setup_replication.sh          # one-time (restarts both postgres instances)

# quick verification (switch after 18s, run 80s total)
./run_test.sh

# long run: 5 minutes total, switch after 90s (the main verification run)
./run_test.sh 300 90

# one-way demo: verify post-switch rows really DO land on the new instance only
REVERSE=0 ./run_test.sh 80 18   # db2 ends up with MORE rows than db1
```

`switchover.sh` can also be used on its own, e.g. to flip back:

```bash
./switchover.sh 5433    # 5432 -> 5433
./switchover.sh 5432    # 5433 -> 5432
```

(The last `run_test.sh` leaves the proxy pointing at 5433; `switchover.sh 5432`
or the RELOAD inside `run_test.sh` resets it.)

## 4. Watching it live (pgbouncer admin console)

```bash
# if the proxy isn't running yet (e.g. right after setup, before run_test):
pgbouncer -d pgbouncer/pgbouncer.ini

psql -h 127.0.0.1 -p 6432 -d pgbouncer -U pgbadmin
```

Handy one-liner: `psql -h 127.0.0.1 -p 6432 -d pgbouncer -U pgbadmin -c 'SHOW POOLS;'`

- `SHOW DATABASES;` — which postgres each db alias currently points at
- `SHOW SERVERS;` — active pgbouncer↔postgres server connections
- `SHOW POOLS;` — `cl_waiting` = clients buffered (paused), `maxwait` = longest
  buffered wait, `cl_active` = clients currently inside transactions
- `PAUSE;` / `RESUME;` / `RELOAD;` — the operations used by the switchover script

Useful postgres-side checks:

```sql
-- replication slots (confirmed_flush_lsn drives the catch-up loop)
SELECT slot_name, active, confirmed_flush_lsn FROM pg_replication_slots;

-- the subscription worker status
SELECT * FROM pg_stat_subscription;

-- who is currently executing on this instance
SELECT pid, state, query FROM pg_stat_activity WHERE state <> 'idle';
```

## 5. What the fixture measures

The app (`-v`) logs every transaction: its tag `inet_server_port()` (which
postgres instance actually executed it), latency, and the spawn→INSERT delay.
At the end it prints:

- `committed via port 5432 / 5433` totals — proof that traffic moved
- a per-10s-bucket timeline — how the boundary looked as it happened
- `spawn->INSERT p50 / p95 / max` — the p95/max spike is the pause window
  (buffering, not errors)
- `FAILED: n` — must be 0 for the test to pass

Acceptance assertions in `run_test.sh`:
- reverse mode (default): 0 failures AND row counts identical on both
  instances (every post-switch insert replicates back to db1 in real time)
- `REVERSE=0` mode: 0 failures AND db2 has strictly more rows than db1
  (i.e., post-switch rows genuinely exist only on the new instance)

## 6. Caveats & limitations

- **Concurrent bidirectional writes**: with `origin='none'`, each subscription
  only applies *local* changes of its publisher. If both sides accept writes
  at the same time (e.g., writes to db1 while db2 is already primary), we're in
  multi-master territory: a row updated on both sides = conflict (one side
  silently wins, depending on apply order). A real switchover keeps writes
  one-sided per direction.
- **REVERSE=0 switchover-back**: if the reverse subscription is deleted, after
  switching writes to db2, db1 no longer receives them, and switching *back*
  to db1 later would leave db1 without those rows. If a switch-back is planned,
  re-create the reverse subscription (`sub_names_reverse`) before or right
  after switching.
- **PG-level `ALTER SYSTEM SET wal_level='logical'` requires restart**;
  `max_slots/max_worker_processes` defaults (10/8) comfortably hold the
  subscriptions created here.
- **The 10s-held-transaction shape is the worst case for drain time** — the
  pause window is bounded by the oldest in-flight transaction.
- **`query_wait_timeout`**: if the drain + catch-up window ever exceeded 120s,
  buffered clients would be dropped with an error. That's a deliberate
  trade-off (fail fast instead of queueing indefinitely); tune if larger
  drains are expected.
- **Sequences**: if more tables with identity columns are added, extend the
  `setval` block (or switch to UUIDs / interleaved ranges to skip the
  operational step).
- **DDL**: schema changes are applied manually on both sides BEFORE altering
  the table on the publisher — the subscriber's apply worker errors and lags
  until its local schema matches.
- **Security (for real deployments)**: this repo uses `auth_type=trust` +
  plaintext no-password entries because it's a local lab. For anything
  exposed/inter-cloud: switch to `scram-sha-256` with real passwords in
  userlist, restrict `listen_addr`, and wrap replication + client traffic in
  TLS.

## 7. Troubleshooting

| symptom | likely cause / fix |
|---|---|
| `PAUSE` hangs | long-running tx that never commits; check `pg_stat_activity` on the old primary |
| post-switch inserts fail with `duplicate key value violates unique constraint "names_pkey"` (23505) | step `[3/6]` sequence seeding skipped or ran before drain finished; re-run the script. NB: stale rows from a previous test run cause the same error — `run_test.sh` resets the dataset each run (set `SKIP_SETUP=1` to opt out) |
| `switchover.sh` fails waiting for catch-up | subscription inactive, e.g. publisher unreachable; check `pg_stat_subscription`, pg logs |
| app reports `server conn crashed / reset` only during switch | likely `query_wait_timeout` too low, or max_client_conn too small so buffered clients get refused |
| db1/db2 row counts drift after run | check whether the reverse sub exists (`REVERSE=1`), check `pg_subscription_rel` states and pg logs |

## 8. Q&A synopsis

**How much did transaction time skew during the switch, and do we need longer
connection/timeout budgets?**
The pause window is bounded by the oldest in-flight transaction — in our runs
~10s (p50 spawn→INSERT stayed ~2ms; p95 spiked to 1–6s; max ~10s). No client
errors because requests *buffer* while paused. Three knobs govern the budget:
pgbouncer's `query_wait_timeout = 120` (how long a buffered client may sit —
this is what an app-side "connection/tx timeout" competes with; it must exceed
our drain window, and app timeouts must in turn exceed it), the app's per-tx
deadlines, and drain duration itself. Pool mode is `transaction`, which is
what makes drain cheap: PAUSE waits on transaction boundaries, not sessions.

**How do we reduce load during initial snapshot propagation (big tables)?**
`copy_data=true` already runs async (background table-sync workers), but for
large tables it holds a long `xmin` snapshot (bloat risk on the publisher),
accumulates WAL behind the slot (disk risk), and decodes everything back.
Reductions: run the initial copy in a lean window; raise
`max_sync_workers_per_subscription` (parallel per *table* — partition giant
tables); tune `logical_decoding_work_mem`; or avoid the window entirely with:
`PAUSE` (freeze writes) → `pg_dump --data-only` → restore →
`CREATE SUBSCRIPTION (copy_data=false)` → `RESUME`. Zero gap because writes
never happened while paused.

**pgbouncer admin console access?**
`psql -h 127.0.0.1 -p 6432 -d pgbouncer -U pgbadmin` then
`PAUSE; / RESUME; / RELOAD; / SHOW DATABASES|POOLS|SERVERS|CLIENTS;`.
(`pgbadmin` is defined in the generated `userlist.txt` and `admin_users`.)

## 9. Blueprint for inter-cloud migration in a lean window?

**Mostly yes.** The core loop — proxy-buffered traffic, one-writer-at-a-time
cutover, LSN-verified catch-up before RESUME, zero-failure app traffic — is
exactly a safe cloud-to-cloud migration. Caveats before we trust it there:
DDL parity must pre-exist (logical replication moves data, not schema/FKs/DDL
runtime); the sequence-seeding step is needed for every identity column;
cross-region latency stretches drain and catch-up (bump timeouts); replication
slots can stall disk on the source (set `max_slot_wal_keep_size`);
`auth_type=trust` + plain TCP is lab-grade only — use scram + TLS; pgbouncer
itself is SPOF (run a redundant pair in front); keep writes one-sided (the
`origin='none'` bidirectional setup assumes no simultaneous multi-master
writes). The `sync_commit` decision is orthogonal (availability vs RPO ~0) —
see §8 and `synchronous_standby_names` in the runtime-config docs.
